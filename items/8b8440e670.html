CVE-2026-98432 是 Linux 内核 IPv4 TCP 握手代码中的一处释放后使用缺陷。内核 CVE 团队 2026年10月24日将其评为 9.8 分；Anthropic 2026年10月27日称，其内部一个研究模型写出了可用利用代码，可让未登录的远程攻击者拿到 root shell，但 Anthropic 未公开代码、内核版本与测试配置。缺陷机理是一场竞态：TCP 连接完成时，tcp_v4_syn_recv_sock() 把请求套接字的 IP 选项交给新建的子套接字而不复制；若同一请求的重传 SYN 在另一个 CPU 上到达，该 CPU 仍在读取这些选项构造 SYNACK，而子套接字已被释放；选项内存以普通 kfree() 释放，未经过 RCU 宽限期，于是 SYNACK 代码读到已释放内存。按 CVE 记录的评分说明，攻击者发送携带 IPv4 Record Route 或 Timestamp 选项的 SYN，再以重传 SYN 与同一连接的完成与拆除过程竞速；整个过程发生在应用看到连接之前，不涉及登录；若已释放内存被重新占用，内核可能在 SYNACK 中泄露堆内容、越界写入或 panic。IPv6 不受该缺陷影响，因为 IPv6 路径会复制选项。缺陷可追溯至 Linux 4.4，上游稳定版修复版本为 5.10.272、5.15.223、6.1.190、6.6.159、6.12.113、6.18.56、7.2.10、7.3-rc7 及更新版本；各厂商评分不一，内核 CNA 按低攻击复杂度评分，Red Hat、Oracle 与 SUSE 按高攻击复杂度评 8.1 分，Amazon 评 7.0 分。Anthropic 的利用针对 MPTCP 监听器：利用泄露内核指针绕过 KASLR 用时 48 分钟，约 5 分钟后达到命令执行；一次竞速失败只会丢弃该次握手，不会使宿主机崩溃，攻击者可以不断重试。MPTCP 监听器比管理员通常以为的更常见：net.mptcp.enabled 的 sysctl 默认值为 1，自 Go 1.24 起 net.ListenConfig 在 Linux 上默认使用 MPTCP；以较新工具链构建的 Go 服务除非程序或内核关闭，否则会以 MPTCP 监听；没有 MPTCP 监听器的服务器未被证明安全，只是落在 Anthropic 测试范围之外。截至 2026年10月30日，Debian 已发布修复（Trixie 为 linux 6.12.113-1，DSA-6568-1；Bookworm 为 linux 6.1.190-1，DLA-4841-1 与 linux-6.12 6.12.113-1~deb12u1，DLA-4850-1）；Ubuntu 22.04、24.04、26.04 与 26.10 的修复处于进行中，尚无 Ubuntu 安全通告，16.04、18.04 与 20.04 列为受影响，14.04 不受影响；RHEL 8、9 与 10 受影响且无修复内核，Red Hat 称没有符合标准的缓解措施，RHEL 7 不受影响；Oracle Linux 的 UEK 内核 2026年10月16日已修复；Amazon Linux 2023 的 kernel6.18 与 kernel6.12 产品线已有修复；SUSE 的 openSUSE Leap 16.0 与 SUSE Linux Micro 6.2 已修复。容器共享宿主机内核，重建镜像无济于事，必须更换宿主机或虚拟机内核并重启。过渡措施分三步：用 ss -lnMp 列出 MPTCP 监听服务，Go 程序可在服务环境中设置 GODEBUG=multipathtcp=0 恢复 Go 1.24 之前的普通 TCP 行为，系统级设置 sysctl net.mptcp.enabled=0 可阻止新建 MPTCP 套接字，但已存在的监听器须重启服务后才消失，须再次运行 ss -lnMp 核对；以 nftables 在连接跟踪之前丢弃携带 IP 选项的入站 IPv4 TCP 包（匹配 IPv4 头长度大于 20 字节），该规则为社区缓解措施而非厂商方案，写入 /etc/nftables.conf 或防火墙管理器配置才能在重启后保留，且不得用于依赖 CIPSO 标签（SELinux 或 Smack NetLabel）而正常使用 IP 选项的宿主机；限制可直达 TCP 监听端口的来源范围，只接受 CDN 或负载均衡地址段的源站不会直接收到攻击者的 SYN。修复确认方法：Debian 上以 uname -v 输出的包版本对照修复版本；RHEL 系在修复发布后以 rpm -q --changelog kernel-core-$(uname -r) 检索 CVE-2026-98432，无输出即表示运行内核不含修复，即使已安装更新的包。

原文

CVE-2026-98432 is a use-after-free in the Linux kernel's IPv4 TCP handshake code. The kernel CVE team rated it 9.8 on October 24, and on October 27 Anthropic said one of its internal research models had written a working exploit that gives an unauthenticated remote attacker a root shell. As of October 30, Debian, Oracle Linux, SUSE and Amazon Linux have shipped fixed kernels for at least some releases. Ubuntu and Red Hat Enterprise Linux have not. When a TCP connection completes, tcp_v4_syn_recv_sock() hands the request socket's IP options to the new child socket without copying them. If a retransmitted SYN for the same request arrives on another CPU, that CPU can still be reading those options to build a SYNACK when the child socket is freed. The options are freed with a plain kfree() instead of after an RCU grace period, so the SYNACK code reads freed memory. According to the CVE record's scoring notes, the attacker sends a SYN carrying IPv4 Record Route or Timestamp options, then races a retransmitted SYN against completing and tearing down the same connection. This happens before the application sees a connection, so no login is involved. If the freed memory is reclaimed, the kernel can leak heap contents in the SYNACK, write out of bounds, or panic. IPv6 is not affected by the main bug because the IPv6 path copies the options. The bug dates to Linux 4.4. The fix is in these stable releases: 5.10.272, 5.15.223, 6.1.190, 6.6.159, 6.12.113, 6.18.56, 7.2.10, 7.3-rc7 and later. Severity scores differ by vendor. The kernel CNA scores attack complexity as low because the attacker controls both sides of the race. Red Hat, Oracle and SUSE score it 8.1 with high attack complexity, and Amazon scores it 7.0. Anthropic's October 27 research post says the exploit works against Linux servers with a multipath TCP listener. It leaked a kernel pointer to defeat KASLR in 48 minutes, then reached shell command execution about five minutes later. A lost race fails only that handshake without crashing the host, so an attacker can keep retrying. Anthropic did not publish the code, the kernel version, or the configuration it tested. Neither the CVE record nor the kernel patch mentions MPTCP. MPTCP listeners are more common than most administrators assume. The sysctl net.mptcp.enabled defaults to 1, and since Go 1.24, net.ListenConfig uses MPTCP by default on Linux. A Go service built with a recent toolchain will listen with MPTCP unless the program or kernel turns it off. A server with no MPTCP listener has not been shown to be safe; it only falls outside the configuration Anthropic tested. No vendor, CISA, or Anthropic has reported exploitation in the wild as of October 30. Distribution status on October 30: Debian fixed, Trixie in linux 6.12.113-1 (DSA-6568-1), Bookworm in linux 6.1.190-1 (DLA-4841-1) and linux-6.12 6.12.113-1~deb12u1 (DLA-4850-1). Ubuntu 22.04, 24.04, 26.04 and 26.10 show fixes in progress, with no Ubuntu Security Notice yet; 16.04, 18.04 and 20.04 are listed as vulnerable; 14.04 is not affected. RHEL 8, 9 and 10 affected, no fixed kernel, and Red Hat says no mitigation meets its criteria; RHEL 7 is not affected. Oracle Linux UEK kernels fixed October 16. Amazon Linux 2023 kernel6.18 and kernel6.12 streams have fixes; Amazon Linux 2 is pending. SUSE openSUSE Leap 16.0 and SUSE Linux Micro 6.2 are fixed. Containers share the host kernel, so rebuilding images does not help. The host or VM kernel has to be replaced and rebooted. Interim steps for Ubuntu and RHEL servers: list services listening with MPTCP with sudo ss -lnMp; for Go programs, setting GODEBUG=multipathtcp=0 in the service environment restores pre-1.24 plain TCP behavior; setting sysctl -w net.mptcp.enabled=0 blocks new MPTCP sockets system-wide but leaves existing listeners open, so restart the affected services and run ss -lnMp again. Drop inbound IPv4 TCP packets that carry IP options with an nftables rule running before connection tracking and matching IPv4 headers longer than 20 bytes. This is a community mitigation, not a vendor one. The rule does not survive a reboot unless added to /etc/nftables.conf or the firewall manager's config. Do not use it on hosts that rely on CIPSO labeling (SELinux or Smack NetLabel), where IP options are normal. Limit who can reach TCP listeners: an origin server that only accepts connections from a CDN or load balancer's address ranges cannot receive the attacker's SYN directly. Confirming the fix after reboot: on Debian, uname -v prints the package version of the running kernel; compare it with the fixed versions above. On RHEL-family systems, once the update ships, rpm -q --changelog kernel-core-$(uname -r) | grep CVE-2026-98432; no output means the running kernel does not have the fix, even if a newer one is installed.
