Java4Shell 自查指南：三道关卡决定是否受影响，查 Java 版本、CPU 指令集与容器基础镜像

正文 · AI 翻译

2026 年 11 月 17 日，OpenJDK 与 Oracle 披露并修复了 CVE-2026-114938，昵称 Java4Shell：这是 Java 虚拟机内置的快速 Base64 解码器中的内存损坏缺陷。OpenJDK 评为 8.1 分（CVSS 3.1，攻击复杂度高）；报告该缺陷的研究人员 Calif 按 CVSS 4.0 评为 9.2 分。无论如何，这是一个网络可达、无需登录的缺陷，位于全球部署最广泛的运行时之一。

名字会让人联想到 Log4Shell，确实有一处可比。但理解 Java4Shell 最有用的一点是多数头条遗漏的：同一个应用、同一个 JAR 文件，在一台服务器上可能受影响，在隔壁服务器上却完全安全。是否暴露取决于三件事，且三件必须同时成立。

缺陷本身一句话概括：为了快速解码 Base64，近期版本的 JVM 使用一段手写例程，借助特殊 CPU 指令。通俗地说，畸形的、带填充的 Base64 输入可使该快速解码器越界写出缓冲区。Java 随后会把该输入当作无效拒绝，但此时相邻内存可能已被破坏。经过针对性的、与应用相关的构造，攻击者可将其转化为内存泄露或远程代码执行。

有两点令人意外。第一，Java 的声誉建立在内存安全之上：语言会替人检查数组访问。但 JVM 本身是用 C、C++ 编写的，在这个位置还用了汇编，这些检查须由开发者自己负责。第二，不存在通用利用代码。每个目标都需要专门定制的利用链，研究人员把武器化的、针对特定产品的利用链保密，以便防御方先打补丁。

把暴露程度看作三道关卡。只有三道关卡全开，缺陷才能触及目标；关闭任意一道即不可利用。

第一关——Java 版本。OpenJDK 公告标注 Java 17、21、25 与 27。Java 8 与 11 不在标注范围内。研究人员称，受影响代码在 17 线可追溯到 17.0.6。Oracle 还为其商业 Java SE 的 Java 8“性能”构建（8u511b33-perf）单独列出，因此使用 Oracle 性能构建的组织应专门查阅 Oracle 的公告。运行 java -version 核对，修复构建带有一个额外的第四段版本号：17 线受影响构建如 17.0.21，修复构建为 17.0.21.1；21 线为 21.0.13.1；25 线为 25.0.5.1；27 线为 27.0.1.1。截至 2026 年 11 月 18 日的厂商状态：Amazon Corretto 已于 11 月 17 日发布修复构建（17.0.21.1.2、21.0.13.1.2、25.0.5.1.2、27.0.1.1.4）；Azul Zulu 已于 11 月 17 日发布修复构建（17.0.21.1+2 至 27.0.1.1+4）；Eclipse Temurin 在撰写时 Adoptium API 仍返回 10 月构建，尚未发布修复构建；Red Hat、Ubuntu、Oracle 等应查阅各自厂商公告中的修复包版本。不要忘记容器基础镜像：镜像里的 Java 才是关键，而不是笔记本电脑上的 Java。

为什么当初会有这段快速代码？因为它快。它经由 2022 年 11 月的一次反向移植进入 Java 17 线，起因是解码大输入时提速最高约 19 倍。反向移植请求中甚至写道：“风险：极小。该代码已使用数月，未报告缺陷。”四年后，同一次优化成了严重缺陷。这是共享运行时风险的典型例证：少数工作负载需要的功能发给了所有人。

第二关——CPU（最容易被忽略的一关）。这道关卡让“同一个 JAR 在这里安全、在那里暴露”成为现实。有缺陷的快速路径只存在于支持 AVX-512 VBMI 指令集的 x86-64 CPU 上。没有该指令集的 CPU 上，JVM 根本不会生成这段代码；ARM 上完全不适用。ARM（AWS Graviton、Apple Silicon 等 ARM64）不受影响。“有 AVX-512”还不够：Intel Skylake-SP 与 Cascade Lake 至强有 AVX-512 但没有 VBMI——关卡关闭；Ice Lake 及更新的至强、AMD Zen 4 及更新（EPYC Genoa/Turin）有 VBMI——关卡打开；较旧的 AMD Zen 3（Milan）完全没有 AVX-512——关闭。对应常见的 AWS 实例族（须以标志检查为准，因为虚拟机只能看到 hypervisor 暴露的内容）：关卡关闭的有 M5（Skylake-SP/Cascade Lake）、M6a（AMD Milan，Zen 3）、Graviton 系列（M7g 等，ARM）；关卡打开的有 M6i（Ice Lake）、M7i（Sapphire Rapids）、M7a（AMD Genoa，Zen 4）、M8a（AMD Turin，Zen 5）。实际意义是：同一个容器镜像原封不动，在 m5.large 上安全，在 m6i.large 上暴露；跨混合节点池的自动扩缩容或实例族之间的迁移，无需任何一次部署即可改变暴露面。不要相信实例名，应检查 CPU 标志。Linux 上执行：grep -m1 '^flags' /proc/cpuinfo | tr ' ' '\n' | grep -E '^(avx512f|avx512bw|avx512vbmi|bmi2)$'；若 avx512f、avx512bw、avx512vbmi 与 bmi2 四项全部打印出来，该 CPU 可以运行有缺陷的路径。

第三关——被攻击者输入喂热的解码器。快速例程只有在 JVM 的优化 JIT 编译器多次运行解码器后才会编译使用。在处理真实流量的繁忙服务器上，这是常态而非特例——攻击者可先用普通合法请求把它“预热”。而 Base64 恰恰出现在不可信输入到达的地方：JWT 令牌（每部分均为 base64url）、HTTP Basic 认证头（凭据为 Base64）、data: URL、文件上传与其他编码载荷。研究人员报告，认证与文件上传等普通功能可在广泛使用的 Java 产品与框架中触及该解码器，甚至连接到恶意服务器的 Java 客户端也可能受影响。第三关难以证明已关闭，因此安全假设是它处于打开状态。

这是下一个 Log4Shell 吗？名字引出了这个问题，诚实的回答是：形似，实质不同。Log4Shell 位于一个随应用打包的库（log4j-core），CVSS 10.0，影响任何硬件，已列入 CISA 已知被利用目录，修复方式是升级每个应用中的 JAR；Java4Shell 位于 JVM 本身，CVSS 8.1（CVSS 3.1）/9.2（CVSS 4.0），仅影响带 AVX-512 VBMI 的 x86-64 硬件，撰写时尚未列入 CISA 已知被利用目录，修复方式是升级运行时，JAR 本身无需改动。最后一行改变了检查清单：2021 年须在每个应用内搜寻依赖；这一次应用产物本身没有问题，需要移动的是底下的 Java 运行时，包括 baked 进每个容器镜像的那一份。

应对措施：1. 打补丁升级运行时。迁移到修复构建（看第四段版本号），并在打过补丁的基础镜像上重建容器镜像。这是唯一能彻底关闭关卡的修复。2. 若无法立即打补丁，可用 JVM 启动参数作缓解：-XX:-UseBASE64Intrinsics 关闭加速的 Base64 编解码例程，或 -XX:UseAVX=2 完全禁用 AVX-512（仅 x86-64；ARM 上的 OpenJDK 不识别该参数，会启动失败）。两者均可通过 JAVA_TOOL_OPTIONS 传入，无需修改启动脚本。代价方面，该标志交还的正是 2022 年反向移植带来的收益：Base64 解码速度。Intel 在 2021 年 OpenJDK 评审中的 Base64Decode 微基准测试显示，小输入提速约 1 倍，约 20 KB 缓冲区最高约 19.7 倍。因此小的令牌（JWT、Basic 认证头）几乎不受影响，大 Base64 解码会明显变慢；-XX:UseAVX=2 影响更广，会关闭所有 AVX-512 优化，而不仅是 Base64。应把该标志视为临时措施：今天必须用就先设上，本周内打补丁，然后去掉。

原文

On 17 November 2026, OpenJDK and Oracle disclosed and patched CVE-2026-114938, nicknamed Java4Shell: a memory-corruption bug in the fast Base64 decoder built into the Java Virtual Machine. OpenJDK scores it 8.1 (CVSS 3.1, attack complexity high); the researchers who reported it, Calif, put it at 9.2 under CVSS 4.0. Either way it is a network-reachable, no-login bug in one of the most widely deployed runtimes on earth.

The name invites a comparison with Log4Shell, and there is one worth making. But the most useful thing to understand about Java4Shell is something the headlines miss: the same application, the same JAR file, can be vulnerable on one server and completely safe on the server next to it. Whether you are exposed depends on three things, and all three have to line up.

What the bug is, in one line: to decode Base64 quickly, recent versions of the JVM use a hand-written routine that leans on special CPU instructions. The bug, in plain terms: a malformed, padded Base64 input can make that fast decoder write past the end of its buffer. Java then rejects the input as invalid, but by then neighbouring memory may already be corrupted. With careful, application-specific work an attacker can turn that into a memory leak or remote code execution.

Two things make this surprising. First, Java's whole reputation is memory safety: the language checks array accesses for you. But the JVM itself is written in C, C++ and, in this spot, assembly, where those checks are your own responsibility. Second, there is no universal exploit. Every target needs its own bespoke approach, and the researchers are keeping their weaponised, product-specific chains private so defenders can patch first.

The three gates: think of your exposure as three gates. The bug only reaches you if all three are open. Shut any one and you are not exploitable. All three conditions must hold at once; closing any one (patch the runtime, run on a CPU without AVX-512 VBMI or on ARM, or keep the decoder off the attacker path) removes the exposure.

Gate 1 — your Java version. The OpenJDK advisory marks Java 17, 21, 25 and 27. Java 8 and 11 are not marked. The researchers say the affected code reaches back to 17.0.6 on the 17 line. Oracle additionally lists its own Java 8 "performance" build (8u511b33-perf) for its commercial Java SE, so if you run Oracle's performance build, check Oracle's advisory specifically. Run java -version. The fixed builds carry an extra, fourth version segment: 17: 17.0.21 affected, 17.0.21.1 fixed; 21: 21.0.13 affected, 21.0.13.1 fixed; 25: 25.0.5 affected, 25.0.5.1 fixed; 27: 27.0.1 affected, 27.0.1.1 fixed. Vendor status as of 18 November 2026: Amazon Corretto — fixed builds released 17 November (17.0.21.1.2, 21.0.13.1.2, 25.0.5.1.2, 27.0.1.1.4). Azul Zulu — fixed builds released 17 November (17.0.21.1+2 through 27.0.1.1+4). Eclipse Temurin — at the time of writing the Adoptium API still returned the October builds; no fixed Temurin build had been published yet. Red Hat, Ubuntu, Oracle and others — check your vendor's own advisory for the fixed package version. Do not forget your container base images: the Java inside the image is what matters, not the Java on your laptop.

Why the fast code was there at all: because it is fast. It arrived on the Java 17 line through a backport in November 2022, requested because it decoded large inputs up to about 19x faster. The backport request even noted: "Risk: minimal. This code has been in use for many months, with no bugs reported." Four years later that same optimisation is the critical bug. It is a neat illustration of shared-runtime risk: a feature a few workloads needed shipped to everyone.

Gate 2 — your CPU (the one most people miss). This is the gate that makes "the same JAR is safe here and vulnerable there" true. The vulnerable fast path only exists on x86-64 CPUs that support the AVX-512 VBMI instruction set. On a CPU without it, the JVM never even generates that code; on ARM it does not apply at all. ARM — AWS Graviton, Apple Silicon, other ARM64: not affected. "AVX-512" is not enough. Intel Skylake-SP and Cascade Lake Xeons have AVX-512 but not VBMI — gate shut. Ice Lake and newer Xeons, and AMD Zen 4 and newer (EPYC "Genoa"/"Turin"), have VBMI — gate open. Older AMD such as Zen 3 ("Milan") has no AVX-512 at all — shut. Mapped onto common AWS instance families (always confirm with the flag check below, since a VM only sees what the hypervisor exposes): gate 2 shut — M5 (Skylake-SP / Cascade Lake), M6a (AMD Milan, Zen 3), Graviton — M7g etc. (ARM); gate 2 open — M6i (Ice Lake), M7i (Sapphire Rapids), M7a (AMD Genoa, Zen 4), M8a (AMD Turin, Zen 5). The practical takeaway: one container image, unchanged, is safe on an m5.large and exposed on an m6i.large. Autoscaling across mixed node pools, or a migration between instance families, can change your exposure without a single deploy. Don't trust the instance name — check the CPU flags. On Linux: grep -m1 '^flags' /proc/cpuinfo | tr ' ' '\n' | grep -E '^(avx512f|avx512bw|avx512vbmi|bmi2)$'. If all four of avx512f, avx512bw, avx512vbmi and bmi2 are printed, the CPU can run the vulnerable path.

Gate 3 — a hot decoder fed attacker input. The fast routine is only used once the JVM's optimising JIT compiler has compiled the decoder, which happens after it has run many times. On a busy server handling real traffic, that is normal, not exotic — and an attacker can warm it up with ordinary valid requests first. And Base64 shows up exactly where untrusted input arrives: JWT tokens (RFC 7519 — each part is base64url), HTTP Basic-auth headers (RFC 7617 — credentials in Base64), data: URLs (RFC 2397), file uploads and other encoded payloads. The researchers report that ordinary features such as authentication and file uploads can reach the decoder in widely used Java products and frameworks, and that even a Java client connecting to a hostile server can be affected. Gate 3 is the one you cannot easily prove shut, so the safe assumption is that it is open.

Is this the next Log4Shell? The name begs the question. The honest answer is: it rhymes, but the shape is different. Log4Shell (CVE-2021-44228): lives in a library (log4j-core) you bundle; CVSS 10.0; affected hardware any; on CISA's exploited list yes; the fix is upgrade a JAR in every app. Java4Shell (CVE-2026-114938): lives in the JVM itself; CVSS 8.1 (CVSS 3.1) / 9.2 (CVSS 4.0); affected hardware x86-64 with AVX-512 VBMI only; on CISA's exploited list not as of this writing; the fix is upgrade the runtime; your JAR doesn't change. That last row is the one that changes your checklist. In 2021 you hunted for a dependency inside every application. This time your application artifact is fine — it is the Java runtime underneath it, including the one baked into every container image, that has to move.

What to do: 1. Patch the runtime. Move to a fixed build (look for that fourth version segment) and rebuild your container images on the patched base. This is the only fix that closes the gate for good. 2. If you can't patch immediately, start the JVM with a mitigation flag: -XX:-UseBASE64Intrinsics turns off the accelerated Base64 encode/decode routine, or -XX:UseAVX=2 disables AVX-512 entirely. x86-64 only — OpenJDK on ARM does not recognise it and will fail to start. You can pass either through JAVA_TOOL_OPTIONS without editing start scripts. What the flag costs: the flag gives back exactly what the 2022 backport added: Base64 decode speed. In Intel's own Base64Decode microbenchmark from the 2021 OpenJDK review, the gain was about 1x for tiny inputs and up to ~19.7x for ~20 KB buffers. So small tokens (a JWT, a Basic-auth header) barely notice; large Base64 decodes get materially slower. -XX:UseAVX=2 is broader still — it switches off every AVX-512 optimisation, not just Base64. Treat the flag as a stopgap: set it today if you must, patch this week, then drop it.
