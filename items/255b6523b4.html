Claude Code“不再询问”把口令写进项目文件：1,122 份公开 GitHub 副本含真实凭据

Apiiro 11 月 5 日发布研究（The Hacker News 11 月 7 日报道）：Claude Code 的“允许且不再询问”选项会把含口令或密钥的完整命令以明文保存到项目文件 .claude/settings.local.j…

thehackernews·媒体报道AI应用今日需判断收录 11-08 18:30

正文 · AI 翻译

开发人员在 Claude Code 里批准命令时输入的口令与 API 密钥，正躺在公开 GitHub 仓库里任人读取。用户选择“允许且不再询问”后，Anthropic 的 AI 编程助手会把命令逐字保存到项目设置文件，其中包括口令。软件安全公司 Apiiro 11 月 5 日表示，1,122 份该文件的公开副本至少含有一个凭据，但未验证其中是否仍有效；研究人员本周早些时候通知的一家公司确认其密钥当时有效。该文件是 .claude/settings.local.json。删除它并不能消除泄露，因为旧版本仍留在 git 历史与仓库分支中。研究人员的建议是先轮换：更换该文件曾经保存过的每一个口令、令牌与密钥，然后再清理。Claude Code 默认在运行大多数 shell 命令前先征求确认。用户选择“允许且不再询问”后，它会按权限文档的说明，把一条允许规则保存到项目内的 .claude/settings.local.json，后续会话中匹配的命令不再询问。规则只覆盖提示中给出的内容，有时是一个模式（如 npm test *），有时是一条确切命令；是确切命令时，其中输入的任何口令或令牌都会以明文一并保存。研究人员在公开文件中发现了仍带凭据的已保存命令，并在最新模型 Opus 5.5 与 Fable 5.1 上复现了该行为。Claude Code 会尝试让该文件不进入 git：首次在 git 仓库中写入该文件时，它会把文件加入用户的全局 git 排除规则，该台电脑上的 Git 随后会在所有仓库中忽略它。但这种保护只留在单个用户的单台电脑 git 设置里，对已经提交的文件不起作用。Claude Code 从不把文件加入项目自身的 .gitignore，保护也就不会随项目传播。在研究人员追踪的 1,105 个仓库中，539 个仓库里有一条把 Claude 列为共同作者的提交修改了该文件，研究人员据此认为 Claude 经常会自行提交该文件。Apiiro 搜索公开 GitHub 发现，该文件共有 104,185 份副本，分布在 103,617 个仓库中；约 1.1%（1,122 份）含至少一个凭据，共 1,379 个不同凭据。凭据的判定标准是符合已知密钥格式，或口令、令牌与公开服务器地址相邻，并经 AI 复核同意。研究人员未说明是否有人使用过这些凭据。超过三分之一的凭据可直接打开数据库，包括 379 个数据库口令；其他包括 43 个公开服务器的 SSH 登录、42 个 GitHub、GitLab 与 npm 令牌、23 个 AWS 密钥。这些文件的所有者中包括 63 个组织，多为各规模的软件公司；最严重的案例包括一家数据库厂商自己的管理级云密钥与一个医疗记录应用数据库的属主口令。截至 11 月 2 日，每个含凭据的文件仍在所在仓库的默认分支上，其中一半在仓库中至少已存在 217 天。该文件的旧版本在 509 个仓库中还含有 734 个当前副本中没有的凭据；分支进一步扩散了这些文件，74 个仓库的 211 个分支带有与原仓库相同的凭据。团队有意提交的共享文件 .claude/settings.json 的 76,011 份副本中，298 份也含有凭据，多在允许规则内；加上旧版本与已保存的智能体聊天记录，总计 1,994 个仓库中有 2,539 个凭据。在研究人员比对文档的 16 款编程智能体中，Claude Code 是唯一被确认默认把完整批准命令保存到项目文件的。研究人员给开发人员的建议是：搜索组织 GitHub 中的 .claude/settings.local.json 与 .claude/settings.json，并检查各仓库的 git 历史，即使文件已被删除；先轮换这些文件曾经保存过的全部口令、令牌与密钥，再清理；用 git rm --cached .claude/settings.local.json 停止跟踪本地文件，并加入仓库自身的 .gitignore；在自己的电脑上打开该文件，删除其中每一条含凭据的规则；不要把凭据放进命令，改用凭据管理器提供的变量（如 $DB_URL）引用，让保存的规则只含变量名；批准模式（如 Bash(npm run:*)）而非单条命令。未上传到 GitHub 的副本同样重要：该文件是项目文件夹里的普通 JSON，也可能留在 npm 包、Docker 镜像、zip 压缩包或同步文件夹中。恶意软件此前已在开发人员电脑上搜寻凭据：2025 年 9 月，Shai-Hulud 蠕虫在受感染电脑上运行 TruffleHog 凭据扫描器，该扫描器标记了超过一半的此类文件。常见凭据扫描器会漏掉其中许多文件。研究人员对全部 104,185 份副本运行 gitleaks 与 TruffleHog（未做验证步骤）：1,122 份含真实凭据的文件中，gitleaks 标记 564 份，TruffleHog 标记 643 份，215 份两者均未标记。多数漏检是命令内输入的口令：扫描器寻找已知密钥格式，而 PGPASSWORD=、sshpass -p 或 mysql -p 之后的口令看起来只是普通命令行里的普通词。研究人员给安全团队的建议是：把 .claude/、.cursor/、.gemini/、.specstory/ 等智能体文件夹与智能体记忆文件当作与 .env 文件一样的凭据载体，在笔记本电脑与仓库中同等对待；加入提交前与 CI 凭据扫描，包括 git 历史，并确保扫描器能发现命令内的口令，而不仅是已知密钥格式；把 .claude/settings.local.json 加入组织的 .gitignore 模板；优先检查与公开服务器配对的凭据，因为这些凭据直接给出访问权限。Claude Code 用户此前已报告过该行为：2025 年 8 月 11 日提交的一则缺陷报告称，含 API 密钥与令牌的已批准命令被逐字存入 settings.local.json；自动化机器人在 60 天无活动后于 2026 年 1 月 3 日以“不计划处理”关闭了该报告。截至报道当日，研究人员引用的四则相关报告均已被同一机器人关闭，最近一则在前一天关闭，Anthropic 均未回复。

原文

Passwords and API keys that developers typed into commands they approved in Claude Code are sitting in public GitHub repositories, where anyone can read them. When a user selects "Yes, and don't ask again," Anthropic's AI coding assistant can save the command, word-for-word, including the secret, in a project settings file. Software security company Apiiro said yesterday that 1,122 public copies of that file hold at least one secret, though it did not test whether any still work. One company the researchers notified earlier this week confirmed its key had been live. The file is .claude/settings.local.json. Removing it from a project does not undo the leak, because older versions stay in git history and in forks of the repository. The researchers' advice is to rotate first: change every password, token, and key the file has ever held, then clean up. By default, Claude Code asks before it runs most shell commands. If the user picks "Yes, and don't ask again," it saves an allow rule in .claude/settings.local.json inside the project, according to its permissions documentation. Matching commands then run without asking in later sessions. The rule covers only what the prompt offered. Sometimes that is a pattern, such as npm test *, and sometimes one exact command. When it is the exact command, any password or token typed into it is saved too, in plain text. In public files, the researchers found saved commands with the secret still inside, and they reproduced the behavior with the latest models, Opus 5.5 and Fable 5.1. Claude Code tries to keep the file out of git. The first time it writes the file in a git repository, it adds the file to the user's global git excludes, its settings documentation says. Git on that computer then ignores the file in every repository. That protection stays in one user's git settings on one computer. It does nothing for a file that was already committed, the researchers say. Claude Code never adds the file to the project's own .gitignore, so the protection does not travel with the project. In 539 of the 1,105 repositories the researchers traced, a commit listing Claude as a co-author changed the file. They take this to mean Claude often commits the file itself. Apiiro's search of public GitHub found 104,185 copies of the file in 103,617 repositories, its research write-up shows. About 1.1% of them, or 1,122 copies, hold at least one secret. Together they hold 1,379 different secrets. A value counted as a secret when it matched a known key format, or when a password or token sat beside the address of a public server. An AI reviewer also had to agree. The researchers do not say whether anyone has used these secrets. More than a third of the secrets open a database directly, including 379 database passwords. Others include 43 SSH logins for public servers, 42 tokens for GitHub, GitLab and npm, and 23 AWS keys. Among the owners of these files are 63 organizations, mostly software companies of all sizes. The strongest cases include a database vendor's own admin-level cloud key and the owner password of a medical-records database, the researchers say. As of Monday, every file with a secret was still on its repository's default branch, and in half of those repositories it had been there for at least 217 days. Older versions of the file contain 734 more secrets across 509 repositories that are not present in any current copy, usually because the file was deleted. Forks spread the files further: 211 forks of 74 repositories carry the same secrets as the originals. Secrets also sit in 298 of 76,011 copies of the shared .claude/settings.json file, which teams commit on purpose, mostly inside allow rules. Including those, the older versions, and saved agent chat logs, the total is 2,539 secrets across 1,994 repositories. Of 16 coding agents whose documentation the researchers compared, Claude Code is the only one confirmed to save the full approved command in a project file by default. For developers, the researchers recommend these steps: search your GitHub organization for .claude/settings.local.json and .claude/settings.json, and check each repository's git history for them, even where the files are gone; rotate every password, token and key the files have ever held, before cleaning up; stop tracking the local file with git rm --cached .claude/settings.local.json, and add it to the repository's own .gitignore; open the file on your own computer, even if it was never committed, and delete every rule that contains a secret; keep secrets out of commands, referring to them as variables from a secrets manager, such as $DB_URL, so the saved rule holds the variable name and not the secret; approve patterns, such as Bash(npm run:*), instead of single commands. Copies that never reach GitHub still matter, the researchers say. The file is plain JSON in the project folder, and it can also be left inside an npm package, a Docker image, a zip archive, or a synced folder. Malware has previously looked for secrets on developer machines. In September 2025, the Shai-Hulud worm ran the TruffleHog secret scanner over infected computers, and the scanner flagged more than half of the files as secret. Common secret scanners miss many of these files. The researchers ran gitleaks and TruffleHog over every copy, without the tools' verification step. Of the 1,122 files with a secret, gitleaks flagged 564 and TruffleHog 643, and neither flagged 215. Most misses are passwords typed inside commands. Scanners look for known key formats, and a password after PGPASSWORD=, sshpass -p, or mysql -p looks like an ordinary word in an ordinary command line. For security teams, the researchers recommend: treat agent folders such as .claude/, .cursor/, .gemini/ and .specstory/, and agent memory files, as holding secrets, like .env files, on laptops as well as in repositories; add them to pre-commit and CI secret scanning, including git history, and make sure the scanner catches passwords inside commands, not only known key formats; add .claude/settings.local.json to the organization's .gitignore templates; check credentials paired with a public server first, because those are the ones that give access. Claude Code users have reported this behavior before. An earlier bug report, filed on August 11, 2025, said approved commands with API keys and tokens were being stored word for word in settings.local.json. An automated bot closed that report as "not planned" on January 3, after 60 days without activity. As of today, the four related reports the researchers cite have all been closed by the same bot, the most recent yesterday. None got a reply from Anthropic, they say.

推荐理由
