Oracle 在 AI World 大会上发布了 Fusion Setup Configuration Registry（FSCR），并推出首个公开版本。这是一个开放的 AI 智能体技能库，用于规划、校验与执行 Oracle Fusion Cloud 的配置。

Oracle 本可以把这套实施知识留在专有工具里，却选择以 Universal Permissive License 开源发布，任何客户与合作伙伴都可以使用、检查与扩展。设计之初就内置了审批关卡、失败即停的检查与凭证的安全处理，而不是事后补上。同样重要的是，Oracle 采用开放的智能体约定，而不是绑定某一个 AI 产品：这些技能开箱即用于 Codex，稍作适配也可用于 Claude Code。

对跑过云 ERP 实施的人来说，这改变了起点。过去配置知识存在于工作手册、厂商加速器与顾问的经验中，现在它随产品一起发布，变成智能体可以遵循的形式。智能体可以读取一条需求，对照 Oracle 的配置任务目录找到对应任务，针对真实环境准备并校验数据，在人员批准后加载。顾问的角色从键入配置转向设计配置、复核智能体准备的内容并批准每一次变更。进度记录在 Fusion 内的 Run Book 与项目文件中，而不是电子表格与个人记忆中。

发布后的节奏值得注意。2026 年 11 月 6 日、10 日与 13 日的三次更新共改动 1,026 个文件、新增约 198,000 行；技能从 1,124 增至 1,173，自动化脚本从 402 增至 470，多数新增集中在 ERP 与 SCM（以上数字为作者统计）。

作者用 Gartner 技术成熟度曲线来定位 FSCR：目前处于创新触发期。曲线其余四个阶段说明了它要成为日常做法还需要什么。期望膨胀期：从第一天起度量价值——在第一次试点前先定好手工方法的基线（每项任务耗时、加载前发现的缺陷、返工与每项任务成本），只分享实测结果，不分享预测；从单任务起步，逐步扩展到功能域、支柱与多环境，只宣称已经证明的规模。幻灭低谷期：提前定好治理与安全——明确智能体可以在哪里写入、按环境使用最小权限用户、决定模型上下文中的客户数据如何保护；建立集中管理的共享上下文，而不是让每个项目组在各自机器上各建一套；把组织特有的流程做成自有技能，放在自己分叉的仓库中，再按固定节奏合入官方更新并复核重测。启蒙斜坡期：配置构建、加载前校验、环境比对与 Run Book 跟踪成为见效最快的环节；治理模式随之成熟；Oracle 与社区补齐依赖图、转换与对账技能与测试技能。生产力高原期：智能体准备、人工批准的配置成为大多数项目的标准做法；竞争转向设计判断、行业技能、数据与集成质量及变更管理；配置变成持续性工作，季度更新、漂移检测与环境一致性成为常态化托管服务。

作者的结论是：FSCR 会成为云 ERP 项目的新操作模式，智能体准备、校验并加载配置，人掌握决策。先到达高原的团队，是那些把期望峰值压低、把低谷垫浅的团队：从第一次试点就度量价值、逐步证明规模、提前定好治理，并在承诺更短工期之前先拿出经过验证的实施成果。

原文

Oracle announced the Fusion Setup Configuration Registry (FSCR) during the AI world conference, and published the first public release. It is an open library of AI-agent skills for planning, validating and executing Oracle Fusion Cloud setup.

This is thought leadership of a high order. Oracle could have kept this know-how inside a proprietary tool; instead it published it openly under the Universal Permissive License, so every customer and partner can use, inspect and extend it. It also set the rules of the road from day one, building approval gates, fail-closed checks and secure handling of credentials into the design rather than adding them later.

Just as important, Oracle built on open agent conventions rather than tying FSCR to a single AI product. The skills run with Codex out of the box and, with a little adaptation, with Claude Code. The published design standards and schemas invite the ecosystem to build on a shared foundation instead of rebuilding the basics.

For anyone who has run a Cloud ERP implementation, this changes the starting point. Setup knowledge that used to live in workbooks, firm accelerators and consultants' heads now ships alongside the product, in a form that an AI agent can follow.

The agent can read a requirement, map it to Oracle's catalog of setup tasks, prepare and validate the data against the live environment, and load it once a person approves. The consultant's role shifts from keying in configuration to designing it, reviewing what the agent prepares and approving each change. Progress is recorded in a Run Book inside Fusion and in project files, not in spreadsheets and people's memory.

The pace since then is what caught my attention. Three further drops, on 6, 10 and 13 November, changed 1,026 files and added about 198,000 lines. In under three weeks the registry grew from 1,124 to 1,173 skills and from 402 to 470 automation scripts. Most of the new work landed in ERP and SCM.

Reflecting on what this means, the reference that kept coming to mind was the Gartner Hype Cycle: every new innovation passes through the same five phases, from the first spark to steady, everyday use. Placing FSCR on that curve separates what it changes today from what it will take to change how projects are run.

FSCR sits at the Innovation Trigger today. The other four phases set out what has to happen for FSCR to reach productivity, based on what the repository can and can't offer.

1. Innovation Trigger: everyone starts from the same baseline. The vendor shipped the method. For the first time, Oracle has published implementation know-how as skills an agent can run, tied to its own catalog of 2,616 setup tasks and its own setup APIs. The playing field is reset. Every partner, from global integrators to boutiques, now has the same 1,173 skills, the same Data Loader route and the same approval gates. Accelerators and configuration workbooks that used to set firms apart are now partly common property. Everyone is racing to embed it. Firms are running pilots with Codex and Claude Code, forking the repository and wrapping it in their own delivery frameworks. The release pace signals intent. Three drops in under three weeks show Oracle is investing, and keep the target moving for anyone building on it. A wave of innovation starts. Expect firm-specific skills, add-ons for the gaps, and tooling around the Run Book and project state.

2. Peak of Inflated Expectations: keeping expectations grounded. How high the peak rises depends on how companies present FSCR. Three measures keep it grounded. Measure value from day one. Benefit can only be proven in a real execution, so agree a baseline from the manual method before the first pilot: time per task, defects caught before load, rework and cost per task. Share measured results, not projections. Prove scale step by step. Configuring one task in a sandbox is not a full program. Move from single tasks to a functional area, then a pillar, then multiple environments, and claim only the scale you have shown; today 116 of 1,048 pillar skills ship their own scripts. Build the skills before making promises. Teams need people who understand both Fusion configuration and working with AI agents: reviewing agent output, interpreting it correctly and extending skills. Train for that mix before committing to nirvana.

3. Trough of Disillusionment: softening the fall. The trough is deepest for teams that skip the groundwork. Four measures, in place before the first production change, keep it shallow. Settle governance and security up front. Today the approver is whoever types in the agent session, so add a strong governance and review process. Agree with security and audit teams where the agent may write, use least-privilege users per environment, and decide how customer data in the model's context is protected. Centralize a common context. When every project team runs agents from its own local host, each builds its own context and the pillars drift apart. Establish a centralized context model, hosted in one governed place rather than on individual machines, so every pillar and project team works from the same project state, design decisions, standards and lessons learned. Protect your differentiation and manage releases deliberately. Organization-specific processes and intellectual property are what set an organization apart, so build them as separate skills in your own fork of the repository, where they stay secure and under your organization's control and governance. Then bring in each FSCR release through a simple pull-and-merge routine with a few guardrails: merge on a regular schedule, review what changed, and retest your own skills before the update reaches a live project. Budget for the AI and plan for LLM changes. AI consumption will keep growing as agents take on more of the work, so establish tokenomics early. Cost builds up well beyond the tasks themselves: in routing and planning, the skills and rule files loaded into context, catalog lookups, validation and approval cycles, and reruns after errors. Set budgets, track cost across all of these layers, and tie spend to the value each task delivers. Complex programs will also outgrow a single session, so adopt a summarize-and-restart approach. Model changes will become a common occurrence, and their pace will increase manyfold, so establish a strong evals framework that quickly assesses each emerging model and benchmarks it against your baseline before adoption.

4. Slope of Enlightenment: customers learn where it pays. The sweet spot becomes clear. Configuration build, validation before load, environment comparison and Run Book tracking deliver; graded playbooks replace big-bang adoption. Governance patterns mature. Least-privilege users per environment, pull-request review of frozen load files, a strong approval mechanism, and governance over roles and checkpoints. The gaps get filled. Oracle and the community add dependency graphs for ERP, SCM and CX, conversion and reconciliation skills, and testing skills. Measurements replace claims. Time per task, defects caught before load, configuration accuracy, business outcome and cost per task. Roles are redefined. Consultants design, review and approve; architects write and curate skills.

5. Plateau of Productivity: the new normal. Agent-prepared, human-approved setup is standard practice. Configuration is built, validated and moved between environments this way on most projects. Differentiation moves up the stack. Firms compete on design judgment, industry skills, data and integration quality, and change management, not configuration labour. Commercial models shift. Smaller build teams, aggregated token-based pricing and outcome-based fees. Configuration becomes continuous. Quarterly updates, drift detection and environment parity become an ongoing managed service.

FSCR will become the operating model for Cloud ERP projects: agents prepare, validate and load the setup, and people own the decisions.

Conclusion: FSCR is the new operating model for Cloud ERP projects, and the hype cycle shows that the path there matters as much as the destination. The ones that reach the plateau first will be the ones that keep the peak low and the trough shallow. They will measure value from the first pilot, prove scale step by step, and settle governance early, and show proven implementation outcomes before promising shorter timelines.

Oracle has given every customer and partner the same starting line. What sets them apart now is how quickly they turn that shared foundation into measured, governed and repeatable delivery, and how well they equip their people to move from keying in configuration to designing, reviewing and approving it.
