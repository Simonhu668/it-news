Power Automate 流程故障告警可接入 Teams 与工单：11 月 20 日起公开预览，须用托管环境

官方依据：微软消息中心通知 MC1560957，经 DataForge 2026 年 11 月 26 日文章整理｜适用产品及版本：Power Platform Monitor 自定义告警 + Power Automate 云端流，触发器位于…

dataforge·媒体报道Microsoft 365项目参考收录 11-27 08:39

正文 · AI 翻译

11 月 20 日，微软开放了一项公开预览：Power Platform Monitor 的告警可以启动一个 Power Automate 云端流，该流可将告警详情发送至 Teams、短信或工单跟踪系统。在此之前，自定义 Monitor 告警只能通过电子邮件通知相关人员，或静置于管理中心。

新的触发器位于 Power Platform for Admins V2 连接器中。管理员将自定义告警规则的通知类型设为“连接器”或“电子邮件和连接器”，然后构建一个接收告警并决定发送位置的流。微软的指南将 Teams、Azure DevOps 和 ServiceNow 列为可能的目的地。

没有任何变化是自动发生的。电子邮件通知保持不变，在租户管理员使用该触发器构建流之前，租户不会看到任何变化。

默认邮件会漏掉不少故障。Power Automate 仅在能够识别已知修复方法（例如连接过期）时才发送逐次运行的电子邮件，而一般的作失败不会触发逐次运行的电子邮件。发送过一次邮件后，同一流在 28 天内无法再发送另一封。逐次运行的告警也并非对每个流默认开启。收件人也是一个弱点：微软表示，逐次运行的电子邮件永远不会发送给环境或租户管理员，未共享的个人流只会通知其创建者。如果创建者已经离职，警告可能会落入无人查看的邮箱。每周摘要确实包含一般性失败，但对于供应商发票已停止过账的情况，一周的等待时间太长了。

微软预定义的 Monitor 告警也无法填补这一缺口。云端流告警覆盖每天至少运行 150 次且成功率低于 90% 的流，且不发送通知。每天只处理 40 个订单的流即使每次运行都失败，也不在该告警范围内。预定义的告警也无法启动新的触发器。

触发器只接受数据复核期为 24 小时的规则，因此故障可能要等大约一天才会被人知晓。微软还推出了针对云端流成功率的小时级规则，但预计要到 2027 年 1 月才会将其接入触发器。在此之前，小时级规则只能发送电子邮件，且告警指南规定每个租户最多 10 条小时级规则，另加 50 条每日规则。

许可问题是更大的成本问题。自定义告警仅在托管环境中可用，一旦环境成为托管环境，在其中运行云端流的每个用户都需要合格许可，例如 Power Automate Premium，或者环境需要按流计费。某些 Dynamics 365 许可（包括 Business Central）也符合条件。从 2027 年 2 月起，微软将阻止没有合适许可的用户打开托管环境中的应用，因此仅为了获得告警而转换环境，可能会导致未获许可的应用用户被锁定。

触发器的连接目前还需要租户管理员账号，环境管理员支持据称即将推出。

连接器参考中还有一些影响服务台设计的细节。每日规则目前只报告“已触发”，因此告警无法在流恢复时自动关闭自己的工单。受影响资源列表可能被截断，触发时间以 UTC 到达。工单模板应转换时间、显示受影响资源数量并附上返回管理中心的链接。

触发器还会监听已连接账号范围内的每一条已加入的规则，因此没有条件的流会路由其构建者从未打算处理的告警。应按告警规则 ID 过滤，并将每条规则映射到指定的业务负责人。

路由流本身也可能失败。选择“电子邮件和连接器”可以保留一条独立通道，以防流的连接过期，建议对每条生产规则都使用该选项。

微软将成功率定义为流能够成功运行的频率。一个在把错误金额写入总账后仍干净完成的流，看起来依然健康。运行次数也可作为指标，但微软的指南没有说明，当已关闭的流完全没有运行时，每日规则是否会触发。在依赖运行次数规则之前，应先测试这种情况。

一个下周到来的变化显示了其中的风险。到 12 月 2 日，在 Power Automate 中使用已列入名单的旧模型的 AI 提示将自动迁移至替代模型。例如 GPT-4.1 mini 的提示将迁移至 GPT-6 Luna，微软警告称措辞、格式与指令处理方式可能不同。更改后的发票摘要可能破坏下一步并触发告警，也可能作为一次成功运行通过，但数据是错误的。流内的输出检查是更好的防御措施，应纳入任何接入财务或客户系统的流程自动化。

建议的后续步骤：列出故障会阻断资金、订单、工资或客户响应的流，并为每个流记录负责人与共同负责人；检查这些流是否位于托管环境，然后在转换环境之前核算缺失许可的价格；在托管沙盒中构建一个故意失败的流并让其运行一天，在创建告警规则之前先开启路由流，因为新建的每日规则在创建时即会被评估，可能在路由流开始监听之前就触发；对少数不能等一天的流使用小时级电子邮件规则，并删除未使用的小时级规则，因为已禁用的规则仍计入 10 条上限；为使用 AI 提示的流添加总额、必填字段与记录数的检查，并在 12 月 2 日之前测试这些提示；2027 年 1 月复查设置，届时微软预计小时级规则可与触发器配合工作。

原文

On 20 November, Microsoft opened a public preview that lets Power Platform Monitor alerts start a Power Automate cloud flow. The flow can pass an alert's details to Teams, SMS or a work item tracking system. Until now, a custom Monitor alert notified people by email or sat in the admin centre.

The new trigger sits in the Power Platform for Admins V2 connector. An admin sets a custom alert rule's notification type to Connector, or Email and connector, then builds a flow that receives the alert and decides where to send the details. Microsoft's guidance names Teams, Azure DevOps and ServiceNow as possible destinations.

Nothing happens automatically. Email notifications stay as they are, and a tenant sees no change until a tenant admin builds a flow with the trigger. Anyone searching for the trigger should know that Microsoft's alerts guide calls it "When an alert fires", while the connector reference lists it as "When an alert triggers (preview)".

Power Automate's standard failure emails cover less than many owners assume. Microsoft sends a per-run email only when it can identify a known fix, such as an expired connection, and a general action failure produces no per-run email. After one email, the same flow can't send another for 28 days. Per-run alerts also aren't switched on for every flow by default.

The recipients are a further weakness. Microsoft says the per-run emails never go to environment or tenant admins, and an unshared personal flow notifies only its creator. If that creator has left the business, the warning may land in a mailbox nobody reads. A weekly digest does include general failures, but a week is a long wait when supplier invoices have stopped posting.

Microsoft's predefined Monitor alerts don't fill the gap for smaller firms. The cloud flow alert covers flows with at least 150 runs a day and a success rate under 90%, and it sends no notification. A flow that processes 40 orders a day falls outside that alert even if every run fails. Predefined alerts can't start the new trigger either.

The trigger accepts only rules with a 24-hour data review period, so a failure could wait about a day before anyone hears of it. Microsoft has also launched hourly rules for cloud flow success rates, but it expects to connect those rules to the trigger by January 2027. Until then hourly rules only send email, and the alerts guide caps them at 10 per tenant alongside 50 daily rules.

Licensing is the larger cost question. Custom alerts work only in managed environments, and once an environment is managed, every user running a cloud flow there needs a qualifying licence such as Power Automate Premium, or the environment needs per-flow capacity. Certain Dynamics 365 licences, including Business Central, also count. From February 2027, Microsoft will block unlicensed users from opening apps in managed environments, so converting an environment just to get alerts could lock out app users who aren't licensed.

The trigger's connection also requires a tenant-admin account for now, with environment-admin support described as coming soon. A firm whose Microsoft 365 tenant is run by a managed service provider will need to agree who owns that account and who may edit the flow using its connection.

The connector reference contains details that affect service desk design. Daily rules currently report "Fired" only, so the alert can't close its own ticket when the flow recovers. The list of affected resources can be truncated, and the fired time arrives in UTC, which is 13 hours behind NZ daylight time. A ticket template should convert the time, show the affected resource count and carry the link back to the admin centre.

The trigger also listens to every opted-in rule within the connected account's scope, so a flow without conditions will route alerts that its builder never intended to handle. We'd filter by alert rule ID and map each rule to a named business owner. Firms that already run formal incident management can fold the alerts into their ITIL 4 practices by setting a priority and response time for each rule.

The routing flow can fail as well. Choosing "Email and connector" keeps a separate path open if the flow's connection expires, and we'd use that option for every production rule.

Microsoft defines success rate as how often flows are able to run successfully. A flow that finishes cleanly after writing the wrong amount into a ledger would still look healthy. Run count is also available as a metric, but Microsoft's guide doesn't say whether a daily rule fires when a switched-off flow records no runs at all. Test that case before relying on a run count rule.

A change due next week shows the risk. By 2 December, AI prompts in Power Automate that use a listed older model will move to a replacement automatically. GPT-4.1 mini prompts go to GPT-6 Luna, for example, and Microsoft warns that wording, formatting and instruction handling can differ. A changed invoice summary might break the next step and trigger an alert, or pass through as a successful run with bad data. Output checks inside the flow are the better defence, and they belong in any process automation that feeds finance or customer systems.

Next steps:

- List the flows whose failure would stop cash, orders, payroll or customer responses, and record an owner and a co-owner for each one. - Check whether those flows sit in a managed environment, then price any missing licences before converting an environment. - Build a deliberately failing flow in a managed sandbox and let it run for a day. Switch on the routing flow before creating the alert rule, because a new daily rule is evaluated on creation and could otherwise fire before the routing flow is listening. - Use hourly email rules for the few flows that can't wait a day, and delete unused hourly rules because disabled ones still count towards the limit of 10. - Add checks for totals, required fields and record counts to flows that use AI prompts, and test those prompts before 2 December. - Review the setup in January, when Microsoft expects hourly rules to work with the trigger.
