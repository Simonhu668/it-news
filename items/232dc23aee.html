云虚拟机与他人的虚拟机共享一台物理服务器，虚拟化层负责把每台虚拟机限制在各自的内存中。Terra Security 的研究人员在一台 DigitalOcean droplet 上找到了突破这一边界的方法，证明读取属于物理宿主机的内存是可能的。该缺陷现编号为 CVE-2026-99312，位于 Linux 内核内置的虚拟化层 KVM 中，影响开启嵌套虚拟化的 AMD 处理器宿主机；它在内核中存在了将近四年，由一次安全修复引入。虚拟机看到的是一段从地址零开始的、看似属于自己的物理内存，每个地址都须翻译成宿主机真实内存中的地址。宿主机 Linux 内核中的 KVM 负责建立完成这一翻译的表，即嵌套页表（NPT）。物理 AMD 芯片每次需要未缓存的翻译时都会读取 NPT；它通过一个字段找到顶层页：KVM 为虚拟机的每个虚拟 CPU 维护一个控制块（AMD 称之为 VMCB），其中的 nCR3 字段保存 NPT 顶层页的宿主机地址，研究者称之为 NPT 指针。虚拟机能被限制住的前提，是 NPT 指针指向的页仍归 KVM 所有。有些云允许虚拟机再运行自己的虚拟机，称为嵌套虚拟机。嵌套虚拟机运行时，处理器使用嵌套虚拟机的 NPT 指针；嵌套虚拟机停止时，KVM 会更新外层虚拟机的 NPT 指针，使其重新指向 live 的表。停止嵌套虚拟机的一种方式会跳过这次更新：名为 INIT 的复位信号。外层虚拟机带着此前的 NPT 指针返回，而该指针指向的页已被释放。处理器仍把该页当作外层虚拟机 NPT 的顶层，内核接下来在那里放什么，就决定了虚拟机能触及哪些内存。虚拟机此时持有一个过期指针：指向已被内核释放的页。该页不会空闲太久；虚拟机访问尚未使用过的内存时，KVM 会建立新的 NPT 页，被释放的页会被重新用作其中之一——虚拟机的一张底层表，填满了虚拟机自身页面的宿主机地址。与此同时，过期指针仍指向该页，处理器把它当作顶层读取，取到一个条目并期望得到第二层表的地址，实际得到的却是一条底层条目，即虚拟机某个自身页面的宿主机地址。于是处理器把虚拟机的一页普通内存当作 NPT 的第二层读取。研究者称该页为 Page A；它是虚拟机的内存，其中的每个条目都可由虚拟机写入。处理器现在从 Page A 取第二层，虚拟机可以自己写出表的其余部分，其条目可指向任意选定的宿主机物理页：宿主机内核，或属于其他虚拟机的内存。下一次处理器遍历该表时，虚拟机的代码经由自己写的页表运行，每次内存访问都会落到指定位置。在 DigitalOcean 上，研究者把伪造的表指向约 127 GB 的宿主机内存（只读映射），扫描宿主机的内核版本横幅，以此证明确实有效。写入部分在研究者自己的服务器上演示，伪造的表把一个宿主机内核页映射为可写，虚拟机向其中写入了选定的字节，加载在宿主机内核中的见证模块确认该页确实被改动。2022 年，KVM 曾有另一个缺陷：复位信号把虚拟 CPU 拉出嵌套虚拟机时，它仍运行在嵌套虚拟机的控制块上，随后该控制块被释放。针对该缺陷（CVE-2022-3344）的修复，是在释放任何内容之前先把 CPU 切回外层虚拟机的控制块。Terra 在 PatchSlop 研究中发现，3.2% 的内核 CVE 是由另一 CVE 的修复引入的；这个缺陷也是以同样方式引入的。披露时间线：2026 年 10 月 21 日向 Linux KVM 维护者报告；2026 年 11 月 2 日修复合入主线，11 月 9 日首次打上 v7.4-rc2 标签；2026 年 11 月 17 日发布于稳定版 7.3.5 以及长期支持内核 6.18.64 与 6.12.118；2026 年 11 月 18 日公布 CVE-2026-99312。缓解措施：研究者调查的许多云厂商因未在 AMD 上开启嵌套虚拟化而不受影响。运行 AMD KVM 宿主机的组织应升级到包含修复的内核；无法立即升级时，将 kvm_amd 模块的 nested 参数设为 0，即可关闭嵌套虚拟化并彻底堵住该路径。

原文

A cloud VM shares a physical server with other customers' VMs, and the hypervisor keeps each one confined to its own memory. We found a way through that boundary on a DigitalOcean droplet, and proved it is possible to read memory that belongs to the physical host. The bug, now tracked as CVE-2026-99312, is in KVM, the hypervisor built into the Linux kernel, on AMD CPUs with nested virtualization enabled. It sat in the kernel for just under four years, and it was opened by a security fix. Our VM sees what looks like its own physical memory, starting at address zero. Those addresses are private to the VM, and every one of them has to be translated into an address in the host's real memory. KVM, the hypervisor inside the host's Linux kernel, builds the table that does this: the nested page table, or NPT. "Nested" here means a second layer of translation underneath the page tables our VM manages for itself. KVM keeps the NPT in host kernel memory, out of our VM's reach. The processor, the physical AMD chip that runs our VM's code, reads the NPT whenever it needs a translation it has not already cached. The processor finds the top-level page through a single field. KVM keeps a control block for each virtual CPU of our VM (AMD calls it the VMCB), and its nCR3 field holds the host address of the NPT's top-level page. We call that field the NPT pointer. KVM builds the table, but the processor makes every selection in it, and it treats whichever page the NPT pointer names as the top level. Our VM stays confined only as long as the NPT pointer names a page KVM still owns. Some clouds let a VM run a VM of its own, called a nested VM. While the nested VM runs, the processor uses the nested VM's NPT pointer. When it stops, KVM updates our VM's NPT pointer so it names our live table again. One way of stopping the nested VM skips that update: a reset signal called INIT. Our VM comes back with the NPT pointer it had before which has since been freed. The processor still treats that page as the top level of our VM's NPT, so whatever the kernel puts there next decides which memory our VM can reach. Our VM now runs with a stale pointer: an NPT pointer to a page the kernel has freed. That page does not stay free for long. When our VM touches memory it has not used before, KVM builds new NPT pages for it, and the freed page comes back as one of them: a bottom-level table for our VM, filled with the host addresses of our VM's pages. Meanwhile the stale pointer still names that page, so the processor reads it as the top level. It picks an entry and expects the address of a second-level table. What it finds is a bottom-level entry: the host address of one of our VM's own pages. So the processor reads an ordinary page of ours as the second level of the NPT. We call that page Page A. It is our VM's memory, so every entry in it is ours to write. The processor now takes its second level from Page A, so we write the rest of the table ourselves. Its entries name any host physical page we choose: the host kernel, or memory that belongs to other VMs. The next time the processor walks the table, our VM's code runs through a page table we wrote, so every memory access it makes lands where we say. On DigitalOcean we pointed the forged table at about 127 GB of host RAM, mapped read-only, and scanned for the host's kernel version banner, which we got as a proof of it really working. We demonstrated the write part on our own server, so nobody else's infrastructure was at risk. There the forged table mapped a host kernel page as writable, and our VM put chosen bytes into it. A witness module we had loaded into the host kernel owned that page and reported that it was indeed changed. In 2022, KVM had a different bug: when a reset pulled a virtual CPU out of a nested VM, it kept running on the nested VM's control block, which then got freed. The fix for that bug, CVE-2022-3344, switched the CPU back to the outer VM's control block before anything was freed. In PatchSlop we found that 3.2% of kernel CVEs were introduced by the fix for another CVE. This bug was introduced the same way. Disclosure Timeline: 2026-10-21. Reported to the Linux KVM maintainers. 2026-11-02. Fix merged to mainline, and first tagged in v7.4-rc2 on 2026-11-09. 2026-11-17. Released in stable 7.3.5 and in the 6.18.64 and 6.12.118 long-term kernels. 2026-11-18. CVE-2026-99312 published. Mitigation: Many cloud providers we surveyed were not vulnerable because they did not enable nested virtualization on AMD. 1. Running KVM hosts on AMD? Update to a kernel that carries the fix. 2. Cannot update yet? Set the nested parameter of the kvm_amd module to 0. That turns nested virtualization off and closes this path completely.
