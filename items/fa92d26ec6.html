Check Point 管理服务器遭 GT13 入侵：24 台服务器被控，7 月已修复的缺陷仍在被利用

正文 · AI 翻译

一家网络安全公司发现了一起针对 Check Point 安全管理服务器的活跃入侵活动，已确认的攻击发生在 2026 年 10 月 17 日至 11 月 2 日之间，影响全球 22 个组织。

该活动由网络安全公司 GreyNoise 追踪，代号为 GreyNoise Threat 13（GT13），似乎没有针对单一地区或行业。受影响组织的资产分布在美国、英国、爱尔兰、法国、荷兰、希腊、德国、奥地利、保加利亚、波兰、印度、泰国、越南、韩国、中国香港、中国和澳大利亚，涉及金融服务、能源、政府、交通、采矿、工程和制造业等行业。

Check Point 发言人表示：“GreyNoise 文章报道的活动涉及 CVE-2026-16232，这是一个此前已披露的漏洞，已有补丁可用，并不代表新的漏洞或利用技术。我们的首要任务仍然是确保客户安装可用的更新，并遵循 Check Point 已发布的安全加固指南，以限制管理访问并识别可疑活动。最重要的行动是安装针对 CVE-2026-16232 的可用更新。Check Point 已发布修复程序，并在其 SecureKnowledge 建议中提供了详细的缓解与调查指南。”

GreyNoise 尚未将 GT13 归因于任何已知或公开追踪的威胁组织。

“入侵 Check Point 安全管理服务器特别严重，因为它不只是企业网络中的另一台服务器。它实际上是管理组织防火墙基础设施与安全策略的中央控制点，拥有高度特权访问权限，”Primus Partners 联合创始人兼董事总经理 Devroop Dhar 表示。他说，根据部署方式和获得的访问级别，其后果可能远远超出安全基础设施本身，可能暴露敏感数据和关键业务应用，并扰乱企业运营。

威胁行为者通过 99 个 IP 地址开展活动，主要经由 ExpressVPN 或被入侵的 Check Point 设备向外路由，产生了 1,400 多个网络会话、800 多条命令行记录以及 1,200 多个创建、上传或下载的文件。

GreyNoise 于 2026 年 10 月 2 日首次观察到该行为者扫描并利用一台 Rejetto HFS 服务器。随后攻击者将这台服务器作为中继，用于管理与已被入侵的 Check Point 设备的交互。

一旦中继建立，攻击者便用它来管理与已被入侵的 Check Point 设备的交互，在针对受害者 A 深化入侵的同时，对其他 21 个受害组织的资产执行批量操作。整个活动期间，攻击者依赖了至少 30 个 Python 脚本，包括辅助脚本、启动器、漏洞探测器和利用运行器。

在 10 月 20 日至 26 日之间，攻击者让一台已被入侵的受害者 A 资产下载并以客户端模式运行 Chisel，从而进一步扫描并与受害者 A 的环境交互。通过 Chisel 隧道，并使用针对 CVE-2026-16232 的脚本，攻击者在多台 Check Point 管理服务器上发起了 100 多项管理任务，包括复制防火墙数据库与内部证书颁发机构（CA）、签发一张新证书（pivot.p12）以及卸载安全策略（这将使防火墙失效）。此外，攻击者还探测了 Citrix NetScaler、Ivanti Connect Secure、VMware vCenter、Microsoft Exchange、Oracle TNS 资产以及多台域控制器。

10 月 26 日，行动转向批量定向：攻击者向 24 台已被入侵的 Check Point 安全管理服务器下发了一项批量证书管理任务。虽然该任务在每台设备上都失败了，但回传的错误日志暴露了受害者的 IP 地址，并显示了一处 /etc/ld.so.preload 对 /usr/lib/.libproc.so 的引用，指向一处可能的植入程序，随后活动暂停至 11 月 2 日。

GreyNoise 推测，GT13 行为者拥有一套成熟的、由 AI 驱动的攻击体系，包括多个将漏洞武器化、扫描易受攻击资产并自动实施利用的智能体框架与系统。

尽管 GreyNoise 对该活动的直接可见性在 2026 年 11 月 2 日前后中断，安全负责人仍须核实各自环境是否已被悄悄渗透。

要确认 Check Point 基础设施是否已被入侵，安全团队应检查管理员登录记录是否存在异常访问模式，包括不熟悉的 IP 地址、异常的登录时间以及未经授权新增的访问权限；还应查看防火墙策略、访问控制规则与配置文件的变更，并彻底审查系统日志、审计轨迹与命令执行历史，寻找可疑活动。

一旦有迹象表明已被入侵，首要任务是防止进一步访问并控制损害。安全团队应将管理服务器的访问限制为仅授权的管理系统，隔离已确认被入侵的系统并保留取证证据；停用未经授权的账户，撤销可疑的 SSH 密钥与访问令牌，并封禁已识别的恶意 IP 地址与域名。

原文

An active intrusion campaign targeting Check Point security management servers has been uncovered, with confirmed attack activity observed between October 17 and November 2, 2026, impacting 22 organizations globally.

Tracked by cybersecurity firm GreyNoise as GreyNoise Threat 13 (GT13), the campaign does not appear to be focused on a single region or industry. Impacted organizations span assets across the US, the UK, Ireland, France, the Netherlands, Greece, Germany, Austria, Bulgaria, Poland, India, Thailand, Vietnam, South Korea, Hong Kong, China, and Australia, across sectors including financial services, energy, government, transportation, mining, engineering, and manufacturing.

"The activity reported by the GreyNoise article involves CVE-2026-16232, a previously disclosed vulnerability with patches already available, and does not represent a new vulnerability or exploitation technique," a Check Point spokesperson said. "Our priority remains ensuring customers apply the available updates and follow Check Point's published hardening guidance to restrict management access and identify suspicious activity. The most important action is to install the available updates for CVE-2026-16232. Check Point has already released fixes and detailed mitigation and investigation guidance in its SecureKnowledge advisory."

GreyNoise has not attributed GT13 to any known or publicly tracked threat group.

"An intrusion into a Check Point security management server is particularly serious because it is not just another server in the enterprise network. It effectively acts as the central control point for managing an organisation's firewall infrastructure and security policies, with highly privileged access," said Devroop Dhar, co-founder and MD at Primus Partners. He said that depending on the deployment and the level of access obtained, the consequences could extend well beyond the security infrastructure itself, potentially exposing sensitive data and critical business applications and disrupting enterprise operations.

The threat actor operated across 99 IP addresses, primarily routed outbound through ExpressVPN or compromised Check Point devices, generating more than 1,400 network sessions, over 800 command-line artifacts, and over 1,200 created, uploaded, or downloaded files.

GreyNoise first observed the actor scanning and exploiting a Rejetto HFS server on October 2, 2026. Each POST to the HFS loginSrp1 endpoint returned a new signed session cookie containing a "sid" value drawn from JavaScript's Math.random() function.

Through conducting several logins in succession, the actor collected enough output to reconstruct the internal state of the V8 PRNG algorithm and thus recover an HFS session cookie signing key, then forge a signed admin session cookie. This allowed the attacker to log in as admin without a password.

A few minutes later, GreyNoise observed that admin requests with forged session cookies were used to gain control of the server. This led GreyNoise to believe that exploitation was indeed CVE-2026-61500 for session forgery, which was not patched on this server. The forged cookie contained "allow_session_ip_change:true", allowing forged cookies to work from any IP address.

On October 5, the actor used this same flow to gain access to install HFS middleware hooks that would issue commands to the compromised server, the research said. This allowed the attacker to append an SSH key to /root/.ssh/authorized_keys. Three days later, on October 8, the threat actor automation check in to the compromised server using the HFS command hook for "uname -a; df -h / | tail -1; whoami".

Instead of using SSH access right away, on October 19, the actor's automated pipeline reused the HFS exploitation route to forge new session cookies and leverage the HFS server_code feature to attempt to download and install additional malware on the server. GreyNoise noted that the idea was to use the compromised server as a relay or "hop" for further intrusion operations.

As the malware download failed, the threat actor returned with a direct SSH connection to continue setting up their relay the next day.

On October 20, the threat actor created a script for setting up an unauthenticated HTTP server on the hop, which they used to upload files. The first exfiltrated .tgz file contained results from a scan of network routes from a compromised Check Point security management server, demonstrating that the actor already had access to targeted victim assets. The actor continued to set up their environment, uploaded and installed open-source tools like Nmap and Chisel, and then set up a Chisel server as a reverse proxy.

Once the compromised server was established as a relay, the actor used it to manage interactions with previously compromised Check Point devices, actively deepening their intrusion against Victim A while conducting bulk actions across 21 other victim organizations. Across the campaign, the operator relied on at least 30 Python scripts, including helpers, launchers, vulnerability probes, and exploit runners.

Between October 20 and 26, the attacker had a compromised Victim A asset download and run Chisel in client mode, allowing them to further scan and interact with Victim A's environment. Over the Chisel tunnel, and by using a script for CVE-2026-16232, the actor launched over 100 management tasks on multiple Check Point management servers. This included copying the firewall database and the Internal CA, minting a new certificate (pivot.p12), and unloading security policies (which would disable the firewall). Further, the actor probed Citrix NetScaler, Ivanti Connect Secure, VMware vCenter, Microsoft Exchange, Oracle TNS assets and several domain controllers.

Between October 20 and 21, the attacker focused on Victim A, first using exploit.py (CVE-2026-16232) against one Check Point server before scanning a second with spray_portal.py. When that second device failed to report back to the relay box, the actor created pull_<redacted_id>.py to steal credentials, internal CA files, and firewall configurations through the first compromised server.

The attacker then expanded inside Victim A's network, running broad port scans with curl, telnet, nmap, and a domain controller probe, followed by targeted exploits against internal Microsoft Netlogon, Citrix NetScaler, Ivanti Connect Secure, Microsoft Exchange, and VMware vCenter servers. They wrapped up this phase by running comb.py, ssh_comb.py, and ssh_spray.py populated with victim-themed usernames and passwords.

On October 26, the operation shifted to bulk targeting. The actor issued a bulk certificate management task to 24 compromised Check Point Security Manager servers, including those belonging to Victim A and 21 other victim assets. Results were shipped in a text file to the hop server that contained an incrementing IP order to run the commands on the compromised Check Point servers and deliver them via SCP to this exfil folder. Although the task failed on every device, the error logs sent back to the hop server exposed victim IP addresses and revealed an /etc/ld.so.preload reference to /usr/lib/.libproc.so, pointing to a likely implant before activity paused until November 2.

GreyNoise suspects the GT13 actor has a mature AI-enabled offensive apparatus including separate agentic harnesses and systems weaponizing vulnerabilities, scanning for vulnerable assets, and automatically exploiting.

Although GreyNoise's direct visibility into the campaign paused around November 2, 2026, security leaders must still verify whether their environments have been quietly infiltrated.

To establish whether Check Point infrastructure has been compromised, CISOs and security teams should examine administrative login records for unusual access patterns, including unfamiliar IP addresses, unexpected login times, and unauthorised access added Dhar. They should also look for changes to firewall policies, access-control rules, and configuration files, and thoroughly review system logs, audit trails, and command execution history for suspicious activity.

Dhar noted that once there are indications of a compromise, the immediate priority should be to prevent further access and contain the damage. Security teams should restrict access to the management server to authorised administrative systems and isolate confirmed compromised systems while preserving forensic evidence. Unauthorised accounts should be disabled, suspicious SSH keys and access tokens revoked, and identified malicious IP addresses and domains blocked.
