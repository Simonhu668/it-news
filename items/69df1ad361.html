攻击者滥用 CyberPower PowerPanel Business 在域控制器上以 SYSTEM 权限执行命令并导出活动目录数据库

官方依据：Symantec 11 月 18 日入侵报告，经 Cyber Security News 11 月 19 日报道｜适用产品及版本：CyberPower PowerPanel Business（UPS 管理软件），攻击经其 Web…

cybersecuritynews.com·媒体报道安全与运维今日需判断收录 11-19 18:30

正文 · AI 翻译

攻击者滥用管理不间断电源（UPS）的 CyberPower PowerPanel Business 软件，在一台 Windows 域控制器上获得了 SYSTEM 级访问权限。Symantec 于 11 月 18 日报告，攻击者利用该软件内置的脚本功能复制了活动目录数据库，并启动了一个在收集活动结束后仍持续运行的恶意软件。研究人员未观察到数据离开网络，也未看到勒索软件被部署。PowerPanel Business 帮助企业在短暂断电期间保持服务器运行，并在较长时间断电时安全关机；其事件设置允许管理员在电力下降或中断时运行脚本。在 Windows 上，PowerPanel 服务 ppbed.exe 以 SYSTEM 身份运行，这是一个拥有广泛本地权限的内置账户，由该服务启动的脚本继承这些权限。在这起事件中，Symantec 将未授权脚本追溯到 TCP 3052 端口上的 PowerPanel Web 控制台。该服务启动了 Windows 命令提示符，随后的活动包括下载工具，以及运行一段 PowerShell 测试——它把一个小型 .NET 程序加载进内存，该程序只打印了一句问候，但证明攻击者可以通过受信任的服务在内存中执行代码。Symantec 未确认攻击者最初是如何获得控制台访问权限的。此前公开资料记载过 PowerPanel Business 的硬编码凭证、默认管理员密码与文件上传缺陷；被盗管理员凭证也是另一种可能。攻击者反复修改收集脚本并在每次尝试后检查结果，最终复制了活动目录数据库 ntds.dit，并收集了 SYSTEM 注册表配置单元。Symantec 表示，反复调整说明有人在实时操作这些工具；它未指明威胁组织，也未确定攻击者的动机。同一 PowerPanel 进程树随后又引出了 upnpcont.exe——一个以微软组件命名的可执行文件，从 SYSTEM 用户配置文件下的异常位置运行，并加载了一个恶意的 atl.dll。这种被称为 DLL 侧加载的技术利用合法程序加载恶意代码库；与 ppbed.exe 的关联让防御者得以把该恶意软件与此前的活动联系起来。Symantec 建议：找到每一处 PowerPanel Business 安装，把 TCP 3052 端口的访问限制在获批的管理员工作站；控制台不要暴露在公共互联网上，也不要放在普通用户网络中。应用厂商更新，把默认密码换成唯一凭证，并检查把电力事件与脚本关联的设置；检查 extcmd 与 temp\profile\extcmd 文件夹中与已知配置不符的脚本。在域控制器上，检查端点日志中与 ppbed.exe 相关的异常命令 shell、PowerShell 活动或数据库访问，并用 Symantec 的事件报告比对文件名与哈希。如果证据显示目录数据库已被复制，即使没有出站传输的证据，也应把域凭证视为可能已暴露，并计划协同重置 krbtgt（用于签署 Kerberos 认证票据的账户）以及更广泛的凭证轮换。

原文

Hackers exploited CyberPower PowerPanel Business software for managing uninterruptible power supplies (UPS) to gain SYSTEM-level access to a Windows domain controller. Symantec reported on November 18 that the attackers used a built-in scripting feature to copy the Active Directory database and launch malware that kept running after the collection activity. Researchers did not observe data leaving the network or see ransomware deployed. PowerPanel Business helps businesses keep servers running during brief power interruptions and shut them down safely during longer outages. Its event settings let administrators run scripts when power drops or fails. On Windows, the PowerPanel service, ppbed.exe, runs as SYSTEM, a built-in account with extensive local privileges. Scripts started by the service inherit those permissions. In the incident, Symantec traced unauthorized scripts to the PowerPanel web console on TCP port 3052. The service launched Windows Command Prompt, and the resulting activity included downloading tools and running a PowerShell test that loaded a small .NET program into memory. The program only printed a greeting, but it showed that the attackers could run code in memory through a trusted service. Symantec did not establish how the attackers first gained console access. Earlier advisories documented hard-coded credentials, a default administrator password and a file-upload flaw in PowerPanel Business. Stolen administrator credentials were another possibility. Cyber Security News previously covered security flaws in PowerPanel Enterprise, a separate CyberPower product. Those findings do not establish how this intrusion began. The attackers repeatedly changed their collection scripts and checked the results before trying again. They eventually copied ntds.dit, the Active Directory database, and collected the SYSTEM registry hive. As our earlier coverage of Active Directory database theft explains, access to both files can expose password hashes and other secrets used to authenticate domain accounts. Symantec said the repeated adjustments suggested someone was operating the tools live. It did not name a threat group or determine the attacker's motive. The same PowerPanel process tree later led to upnpcont.exe, an executable named after a Microsoft component. It ran from an unusual location under the SYSTEM profile and loaded a malicious atl.dll. The technique, known as DLL side-loading, uses a legitimate program to load a malicious code library. The link back to ppbed.exe gave defenders a way to connect the malware with the earlier activity. Symantec recommends finding every PowerPanel Business installation and limiting access to TCP port 3052 to approved administrator workstations. Keep the console off the public internet and away from regular user networks. Apply vendor updates, replace default passwords with unique credentials, and review the settings that link power events to scripts. Check the extcmd and temp\profile\extcmd folders for scripts that do not match a known configuration. On domain controllers, review endpoint logs for unusual command shells, PowerShell activity, or database access linked to ppbed.exe. Use Symantec's incident report to compare file names and hashes with evidence from affected hosts. If the evidence shows that the directory database was copied, treat domain credentials as potentially exposed even without proof of an outbound transfer. Plan a coordinated reset of krbtgt, the account used to sign Kerberos authentication tickets, alongside wider credential rotation.
